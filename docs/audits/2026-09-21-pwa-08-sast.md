# PWA-08 — SAST-Gate in CI: Umfang, Regelsatz, Ausnahmen, Negativnachweis

Stand 2026-09-21. Dieses Dokument schließt den letzten offenen Punkt aus #140 ab
(„SAST-Gate in CI und Hardening-Nachweis"). Es hält den gepinnten Scanner, den
Prüfumfang, die Schwelle, die **Ausnahmen (keine)** und den Beweis fest, dass das Gate
tatsächlich fehlschlagen kann.

Vorgeschichte, damit die verlinkten Dokumente nicht widersprüchlich wirken: PR #147
hatte den Lauf bereits in `scripts/verify.py` und den Entscheidungsnachweis in
`docs/security/pwa-hardening.md` hinterlegt, aber den CI-Job selbst nicht — der Push
auf `.github/workflows/**` wurde damals mangels `workflow`-Scope abgelehnt (auf `main`
existiert bis heute kein `sast`-Job; `gh pr view 147 --json files` zeigt nur
`apps/web/package.json`, `docs/security/pwa-hardening.md`, `pnpm-lock.yaml`,
`scripts/verify.py`). Mit vorhandenem `workflow`-Scope liefert dieser PR den Job nach.

## 1 — Umfang

| | |
|---|---|
| Gescannte Pfade | `apps/api/src`, `packages` (rekursiv, inkl. `packages/*/tests`) |
| Nicht gescannt | `apps/web`, `apps/mobile`, `apps/pdf` (TypeScript/JS — dort greifen ESLint, `tsc`, Vitest und Playwright), `scripts`, Docs |
| Oberfläche | Python (Produktionscode **und** Testcode der Engine-Pakete) |

Der Testcode ist bewusst **im** Umfang: genau er erzeugt die 449 LOW-Funde
(`assert`), und ein Ausschluss wäre ein pauschales Unterdrücken statt einer geprüften
Schwelle. Deshalb trennt nicht der Pfadfilter, sondern die Severity-Schwelle (Abschnitt 3).

Ein Frontend-SAST (z. B. Semgrep auf `apps/web`) ist **nicht** Teil dieses Scopes: #140
verlangt statische Analyse für die Python-Oberfläche, und ein zweiter Scanner würde ein
zweites Regelset-/Version-Regime in die CI bringen. Die harte Frontend-Härtung läuft
weiterhin über `no-floating-promises`/`no-misused-promises` (#136), `tsc --noEmit`,
die Vitest-/Playwright-Suiten und die Coverage-Messung.

## 2 — Scanner, Version, Pin

* **bandit 1.8.6**, gepinnt im Befehl selbst (kein „latest"): `bandit==1.8.6`.
* Regelset: **bandit-Default** — kein `-s`/`--skip`, kein `-t`, keine `.bandit`-/
  `setup.cfg`-/`[tool.bandit]`-Konfiguration existiert im Repo (geprüft), es greifen also
  alle eingebauten Plugins (B1xx/B3xx/B6xx-Blacklists plus die AST-basierten Prüfungen).
* Warum Pinning: ein bandit-Release kann Regeln ergänzen oder Severities verschieben;
  ohne Pin würde derselbe Commit von heute auf morgen rot. Warum bandit und nicht
  semgrep: die Rezeptur existierte bereits (`scripts/verify.py`), das Werkzeug läuft
  offline ohne Regel-Download und ohne bezahlte Stufe, und für eine reine
  Python-Oberfläche ist es das signalärmste Gate (Gap-Analyse G-SEC-03 hatte
  „Semgrep/Bandit" offen gelassen — die Entscheidung ist damit Bandit).

Der Befehl ist an drei Stellen **derselbe** und kann nicht auseinanderlaufen:
CI-Job `sast` (`.github/workflows/ci.yml`), `scripts/verify.py`
(`sast (bandit, medium+)`) und `docs/security/pwa-hardening.md`.

## 3 — Schwelle, Baseline, Ausnahmen

```bash
uv run --with bandit==1.8.6 bandit -q -r apps/api/src packages -ll
```

`-ll` = nur MEDIUM und HIGH. Stand 2026-09-21 auf `main` (`36de60d`), gemessen mit
demselben Befehl plus `-f json`:

```text
bandit 1.8.6 (python 3.11.16)
449 Findings -- alle SEVERITY.LOW, alle Test-ID B101, alle CONFIDENCE.HIGH
0 MEDIUM, 0 HIGH
loc: 24736
```

* **Keine Ausnahmeliste.** Kein `--baseline`-File (eine Baseline friert den Ist-Stand ein
  und macht neue Funde in **alten** Dateien unsichtbar), kein `#nosec`, keine
  Skip-Liste. Der Lauf selbst weist das aus:
  `Total lines skipped (#nosec): 0` und `Total potential issues skipped due to
  specifically being disabled: 0`. Auch die 449 LOW-Funde sind nicht unterdrückt,
  sondern liegen unterhalb der dokumentierten Schwelle — sie erscheinen in einem
  Lauf ohne `-ll` weiterhin vollständig.
* Damit ist das Gate heute grün **und** aussagekräftig: es schlägt bei einem neuen
  medium/high-Fund fehl, statt eine Low-Liste zu verwalten.

## 4 — Negativnachweis (RED → GREEN)

Durchgeführt am 2026-09-21 mit dem **exakten CI-Befehl**, in einer Wegwerf-Fixture
`apps/api/src/zz_sast_gate_negative_fixture.py`, die nie committet wurde
(`git status` nach dem Entfernen leer):

| # | Fixture-Inhalt | Severity | Exit-Code | Ergebnis |
|---|---|---|---|---|
| 1 | nur `assert` (B101) | LOW | **0** | Grenzfall: LOW lässt das Gate grün — die Schwelle ist „MEDIUM+", nicht „irgendein Fund" |
| 2 | `hashlib.md5(...)` (B324) | **HIGH** | **1** | Gate bricht ab |
| 3 | `eval(expression)` (B307) | **MEDIUM** | **1** | Gate bricht ab — der geforderte MEDIUM-Beweis |
| 4 | Fixture entfernt | — | **0** | wieder grün |

Auszug aus Lauf 3 (Exit 1):

```text
>> Issue: [B307:blacklist] Use of possibly insecure function - consider using safer ast.literal_eval.
   Severity: Medium   Confidence: High
   Location: apps/api/src/zz_sast_gate_negative_fixture.py:8:11
...
Run metrics:
	Total issues (by severity):
		Low: 449
		Medium: 1
		High: 0
```

Reproduktion in zwei Zeilen (kein CI nötig, gleicher Befehl wie der Job):

```bash
printf 'def f(e):\n    return eval(e)\n' > apps/api/src/zz_sast_gate_negative_fixture.py
uv run --with bandit==1.8.6 bandit -q -r apps/api/src packages -ll   # -> Exit 1
rm apps/api/src/zz_sast_gate_negative_fixture.py
uv run --with bandit==1.8.6 bandit -q -r apps/api/src packages -ll   # -> Exit 0
```

Hinweis zum Ablauf: Der PR, der den Job einführt, läuft auf `main`-Niveau grün (es gibt
keinen MEDIUM/HIGH-Fund); der Fehlschlag-Fall ist über Lauf 3 oben belegt, nicht über
einen grünen Job. Es gibt bewusst keinen `workflow_dispatch`-Trigger und keine
absichtlich rote Dauer-Fixture im Repo.

## 6 — Bekannte Grenzen (bewusst offen)

* **`sast` ist nicht in den Required Checks der Branch-Protection.** Branch-Protection
  wurde in diesem PR absichtlich nicht angefasst (Merge erfolgt separat nach
  unabhängigem Diff-Review); ohne den Eintrag ist ein roter `sast`-Lauf sichtbar, aber
  nicht merge-blockierend.
* **Keine DAST-/Fuzzing-Stufe** und kein JS/TS-SAST (Abschnitt 1).
* **Hartcodierte englische Fallback-Texte** in `lib/auth-context.tsx` und die
  ungefangene `logout()`-Ablehnung in `app-shell.tsx:269` sind als Beobachtung in
  `docs/security/pwa-hardening.md` §5 notiert — außerhalb des SAST-Scopes, nicht geändert.
