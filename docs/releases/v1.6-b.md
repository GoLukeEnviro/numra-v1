# NUMRA V1.6 B — Public Platform and Admin Console

## Release scope

V1.6 A shipped RBAC and the admin API with no frontend. V1.6 B completes the account
platform: a public landing page, self-service registration with auto-login, a short
onboarding flow, a full admin console frontend, role-aware navigation, and complete
DE/EN localization of the entire product surface (public, signed-in, and admin).

## Auth / session architecture

`POST /v1/auth/register` previously created only a `User` row; the browser had to log
in separately. It now issues the same session + CSRF cookies as `/v1/auth/login`
through one shared internal helper (`_issue_authenticated_session`), so a successful
registration leaves the browser authenticated immediately — no server-side redirect,
the client decides where to navigate. Login's own behavior is unchanged and
regression-tested.

Role and `is_active` come exclusively from `User` model defaults (`USER` /
`true`); `RegisterRequest` has `extra="forbid"`, so any additional key in the body
(`role`, `is_admin`, `is_active`, `permissions`, ...) is rejected with 422 before it
can reach the database.

Email identity is normalized (`strip().lower()`) on both write (`create_user`) and
lookup (`get_user_by_email`), so `Foo@Example.com` and `foo@example.com` can never
become two accounts. A concurrent duplicate registration is caught at the
`IntegrityError` level against the existing unique index — never surfaced as a raw
database exception — and mapped to a stable `EMAIL_ALREADY_REGISTERED` (409).

`GET /v1/public/config` is the one new unauthenticated endpoint. Its response schema
is capped to exactly `self_signup_enabled`, `app_name`, `supported_ui_locales` — no
environment, URL, path, version, or other deployment metadata can leak through it
(enforced by a dedicated leak test asserting the response body never contains
`DATABASE_URL`/`postgresql`/`redis`/`SESSION_SECRET`/`OLLAMA`/`pdf_internal_token`/
`environment`).

One NUMRA auth system throughout — no JWT, no second password store, no second
session mechanism was introduced.

## Admin architecture

The frontend for V1.6 A's already-shipped RBAC/admin API:

- `/admin/login` — same auth backend as `/login`; a USER who successfully
  authenticates sees a clear, friendly "no admin access" message and stays signed in
  (not logged out), with a link back to the normal dashboard. Nothing about a target
  email's admin status is disclosed before authentication succeeds.
- `/admin`, `/admin/users`, `/admin/users/[id]`, `/admin/audit` — server-side
  pagination and filtering throughout, never client-side.
- `AdminGuard` explicitly documents in code that it is **not** the security boundary —
  `require_admin` on the FastAPI router is authoritative. Live-verified: an
  unauthenticated request to `/v1/admin/stats`, `/users`, or `/audit` returns 401; an
  authenticated USER session returns 403 on all three.
- Disable / enable / revoke-sessions go through an accessible confirmation dialog
  (focus trap, ESC to close, no native `confirm()`). An admin viewing their own account
  has "Deactivate" visibly disabled, matching the backend's self-lockout rejection.
- Role-aware navigation: the "Admin" nav entry exists in the DOM only for
  `role === "ADMIN"` — not merely hidden via CSS for USER.

## Privacy boundaries

Admin user views expose only safe metadata and counts — email, role, active/disabled
status, registration/last-login timestamps, and session/people/calculation/report/
relationship *counts*. Never password hashes, session hashes, birth data, Person
content, CanonicalProfile, report text, relationship text, or LLM prompts. Verified
directly against the live admin API response during production acceptance.

## i18n

The flat `de.ts`/`en.ts` catalog (~20 keys, V1.5-era) is now split into
`core`/`public`/`app`/`admin` modules per locale, aggregated by an `index.ts`, still
typed 1:1 against each other (`Record<keyof typeof de*, string>` — a missing or extra
key fails `tsc`). A new `catalog-parity.test.ts` catches what the type system can't:
blank translations, and multi-word strings left byte-identical between locales (an
untranslated copy-paste stub).

Every hardcoded string across the landing page, login, register, onboarding,
dashboard, people, today, reports, relationships, analysis, calculation comparison,
settings, and the entire admin console is now localized, German default. Established
numerology terminology (Life Path, Personal Day, Master Number, Pinnacle, ...) is
deliberately left English — canon-spec-consistent domain vocabulary, not UI chrome.
UI language remains a pure per-browser preference (`numra:locale:v1`) and has never
affected, and still does not affect, report/knowledge/calculation language — the
report content is independently German.

### Known gap in this acceptance pass

Live mobile-viewport verification (390×844, 430×932) against production could not be
completed in this session: the browser-automation tool's window-resize call changed
the outer OS window but the actual CDP-controlled content viewport
(`window.innerWidth`) did not follow it in this environment, confirmed by direct
`window.innerWidth`/`innerHeight` inspection after multiple resize attempts at
different sizes. This is a tooling limitation, not a product finding — reported here
rather than silently skipped or falsely marked as passing. The responsive
implementation itself (server-side-paginated admin tables in a dedicated
`overflow-x-auto` container distinct from a `md:`-breakpointed card layout, the
existing V1.5 mobile bottom-nav pattern extended rather than rebuilt, no new
fixed-width elements introduced) was reviewed at the code level during
implementation, but that is not a substitute for a real rendered-viewport check and is
recorded as such.
